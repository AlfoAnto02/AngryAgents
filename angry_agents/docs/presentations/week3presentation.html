Persona extraction — two-phase pipeline

Source material → structured behavioral fingerprint.

Phase 1 grounds every field in the transcript. Phase 2 adds discriminating model knowledge no transcript can produce.

Phase 1 — Transcript pass
gpt-4o-mini (default)
  • core_style — register, rhythm, sentence shape
  • humor — style, frequency, mechanism
  • worldview — beliefs grounded in the text
  • emotional_tells — pressure, enthusiasm, uncertainty
  • response_patterns — disagreement, deflection, concession
  • relationship_matrix — only real co-speakers
  • annotated_quotes — ≥10 verbatim lines
Phase 2 — Knowledge pass
gpt-4o (per-spec override)
  • favored_words — catchphrases, trademark exclamations
  • structural_patterns — syntactic tics unique to this person
  • do_not_say — ≥5 lines with contradicts annotation
  • No transcript sent — pure model knowledge.
  • Each item must fail the “similar figure” test.
  • Merged into Phase 1 output after both calls.

Chat modes — DM vs group chat

Two chat modes. One persona engine.

The same persona can speak in two different settings: a direct DM with one human, or a group conversation with 2 to 8 agents on a shared topic.

DM chat
  • 1 agent talks to 1 human user.
  • The agent must answer in the user’s language.
  • The prompt is optimized for direct interaction and user instructions.
  • This mode is used for one-on-one conversations, not peer discussion.
Group chat
  • 2 to 8 agents talk to each other.
  • They discuss a given topic inside the same conversation.
  • The user can observe the conversation and interact with the agents.
  • Each agent sees other participants only as labeled speakers, not real identities.
Why templates matter
  • Templates are the system prompt sent to the LLM before generation.
  • They inject the persona profile, topic, history, and writing style into the model context.
  • They also enforce different behavior for DM and group chat.
  • Without templates, the same persona would sound generic and drift more easily.
How the templates work
  • They are Jinja2 system prompts. At runtime, the code renders a different template depending on the chat mode, then passes the filled prompt to the LLM.
  • Group chat template. It gives the model the persona profile, the topic, the conversation history, and explicit writing constraints so each agent speaks like a peer in the group, not like a generic chatbot.
  • DM template. It keeps the same persona profile but changes the instructions: one human user, same-language replies, and direct engagement with the user’s request.
  • They are effective because they separate behavior by mode. The same persona can speak as a peer in group chat or as a direct assistant in DM without losing consistency.
  • The template also adds re-grounding every 20 turns, which reduces persona drift without extra LLM calls.
Group chat — architecture

Eight agents. One shared conversation.

The group chat module keeps each persona consistent, schedules turns fairly, and hides real identities from the judges.

What the system must do
  • Stay in character for dozens of turns without drifting.
  • Call the LLM only when needed, not at every tick of the loop.
  • Keep authors anonymous so judges cannot see who wrote what.
  • Each message author is stored as an HMAC token, not a real name.
Main building blocks
  • PersonaAgent — encapsulates the persona profile and prompt data.
  • TurnScheduler — decides which agent speaks next.
  • ContextWindow — chooses how much history each agent sees.
  • GroupChatSession — runs the conversation and writes messages to the DB.

RAG system — build time

Chunk once. Index once.

Before any evaluation starts, each persona profile is split into semantic chunks and embedded into a persistent vector store.

1 — Chunking
builder.py
  • style — core_style, speech_signature, response_patterns
  • voice — humor, vocabulary_fingerprint, vocabulary_markers
  • worldview — beliefs, ideology, emotional triggers
  • behavior — situational behavior, escalation, social positioning
  • quote — one chunk per annotated quote
  • Each profile becomes 4–9 chunks depending on how rich it is.
2 — Indexing
indexer.py + ChromaDB
  • Each chunk is embedded with text-embedding-3-small.
  • Vectors and metadata are stored in data/chroma/.
  • The index is built once and reused for every evaluation.
  • Quotes are the strongest signal because they preserve rhythm and register.
  • At query time, judges never scan all 100 profiles directly.

Judge phase — evaluation workflow

One judge pass, one tool pass, then metrics and deliberation.

The evaluation starts from a RAG-shortlisted candidate set, then the judges score persona identity and fidelity, and finally the system aggregates the results and runs deliberation on the harder cases.

LLM call 1 — normal judge pass
  • The judge sees the persona profile and the chat history.
  • It scores the anonymised authors and produces the first answer.
  • This pass is used for persona identification and individual fidelity.
  • The candidate set is already shortened by RAG before this call.
LLM call 2 — RAG as a tool
  • The same judge runs again, but can query ChromaDB when the shortlist is not enough.
  • This lets the judge fetch extra evidence instead of being trapped in the initial candidates.
  • The tool-based pass improves robustness on ambiguous or borderline cases.
  • The tool mechanism will be explained in a separate slide.
What happens after scoring
  • The system computes the evaluation metrics from the judge outputs.
  • It then selects the harder or higher-variance cases for deliberation.
  • In Phase 2, judges compare their first pass results and may revise them.
  • RAG remains the entry point, but the core of this slide is the judging process itself.
Judge phase — RAG as a tool

Tool access improves accuracy, especially on semantic fields like ideology.

The judge first evaluates the merged candidate set, then can call RAG as a tool for deeper semantic retrieval when the initial shortlist is not enough. This helps the model reason on harder dimensions, but it also increases token usage and cost.

LLM call 1 — normal judge pass
  • The judge sees the merged list of personas and the chat history.
  • It scores anonymous authors against the candidate personas.
  • This pass produces the first persona identification and fidelity estimates.
  • This pass works, but it struggles more on semantic fields such as ideology.
LLM call 2 — RAG as a tool
  • The same judge can query ChromaDB for the semantic chunks that matter most.
  • This is particularly useful for fields like ideology, where pure prompt reasoning is weaker.
  • It improves accuracy by about 10%, but roughly doubles token usage.
  • In practice, the trade-off is whether the gain in quality is worth the added cost.
