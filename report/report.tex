\section{Introduction}

\textbf{Angry Agents} is a web application in which users interact with AI persona-agents that
faithfully represent real-world or fictional characters --- politicians, influencers, movie and tv series
characters, and more. Conversations can be evaluated by 20 judge-agents
across four fidelity dimensions: persona identification, individual fidelity, group fidelity, and
behavioral fidelity.

The project addresses a research question at the intersection of multi-agent systems, LLM-based
role-playing, and automated evaluation:

\begin{quote}
\emph{Can an LLM, conditioned on a structured persona profile extracted from source material, faithfully
simulate a real or fictional character in a multi-turn conversation, to the point that independent
judge-agents can correctly identify it?}
\end{quote}

\subsection{Interaction modes}

The platform supports two conversation types:

\begin{description}[leftmargin=2cm,labelwidth=1.8cm]
  \item[\textbf{DM}] One user converses one-on-one with a single persona-agent. The agent responds to the user's messages.
  \item[\textbf{Group chat}] The user sets a topic and selects 2--8 agents. The agents start to converse
        autonomously and the user can observe and inject messages.
\end{description}

\subsection{Persona types}

\begin{description}[leftmargin=2cm,labelwidth=1.8cm]
  \item[\textbf{Fiction}] Characters extracted from movie scripts or TV screenplays
        (e.g.\ Batman, Darth Vader, Bart Simpson).
  \item[\textbf{Real-world}] People extracted from podcast transcripts, YouTube videos, and
        social-media corpora (e.g.\ Barack Obama, Andrej Karpathy, Bernie Sanders).
\end{description}

\subsection{User roles}

\begin{description}[leftmargin=2cm,labelwidth=1.8cm]
  \item[\textbf{Common user}] Chat with agents, manage own conversations.
  \item[\textbf{Admin}] Manage personas, launch judge evaluations, view metrics.
\end{description}

\subsection{Phase I --- Foundation (May 5--13)}

\paragraph{Starting from the question.}
The team began not from code but from a research question: can an LLM faithfully simulate a
real or fictional person, to the point that independent judges cannot tell the difference?
Answering this required agreeing on what \emph{faithful simulation} even means --- a question
that took several days of iteration to pin down.

Five papers shaped the answer. Park et al.\ [2023] showed that long-running agents drift toward
generic agreement without memory and reflection mechanisms. Zhou et al.\ [2025] demonstrated that
\emph{personal detail features} --- not surface vocabulary --- are the strongest predictor of
behavioral fidelity. Jiang et al.\ [2024] proved that raters who know they are reading AI output
systematically underestimate personality fidelity, directly motivating a blind evaluation
protocol. These findings were not background reading: they became design constraints.

\paragraph{First data model.}
The earliest database design had six tables: \texttt{Agents}, \texttt{Chat}, \texttt{Chat\_messages}, \texttt{Judges}, \texttt{Judge\_evaluation}, and two separate
context tables for fiction and podcast personas. At this stage the most consequential design
decision was made: the \texttt{author} field in \texttt{Chat\_messages} would store a
cryptographic hash of the agent's identity rather than a foreign key back to
\texttt{Agents}. This single choice encoded the core requirement --- judges must not be able
to link a message to a known persona --- at the schema level, making it impossible to
violate accidentally.

\paragraph{First personas.}
Three scraping pipelines were started in parallel: YouTube transcript extraction for
real-world personas (politicians, podcasters), movie-script PDF parsing for fictional
characters, and IMSDB HTML scraping for additional screenplays. The first eleven fictional
profiles were extracted: Darth Vader, Yoda, Indiana Jones, Jack Sparrow, Luke Skywalker,
Batman, Joker, and others. Each profile was a structured JSON document capturing speaking
style, worldview, emotional tells, and signature phrases --- a format informed directly by
the Zhou et al.\ finding on personal detail importance.

\paragraph{First UI.}
A React prototype with ten components covered the full user journey: authentication, persona
library, DM chat wizard, group chat wizard, active chat, and admin dashboard. It ran entirely
on static mock data. The purpose was not to ship a product but to expose interaction design
questions early, before the backend was complete.

\subsection{Phase II --- Core Pipeline (May 14--24)}

\paragraph{Rethinking the schema.}
The two separate context tables from Phase I were a premature distinction. As the personas grew
in complexity, both fiction and real-world agents needed the same structured JSON profile; the
only difference was the \texttt{source\_type} field. The schema was consolidated: one
\texttt{Agent\_context} table with a \texttt{signature\_phrases} JSON column. A \texttt{Topic}
table was added to give group chats a shared theme. All entities gained
\texttt{created\_at / updated\_at / deleted\_at} timestamps enforced by database triggers,
enabling soft-delete across the board.

The most significant structural addition was the \texttt{User} table. The first schema had no
concept of platform users at all --- agents, chats, and evaluations existed in isolation. Adding
users required propagating a \texttt{Created\_by} foreign key through four tables
(\texttt{Group\_chat}, \texttt{Topic}, \texttt{Agents}, \texttt{Chat\_messages}) and introducing
role-based access (\texttt{common} vs.\ \texttt{admin}). This also unlocked proper authentication:
JWT access tokens (15-minute expiry) paired with httpOnly refresh tokens whose SHA-256 hash is
stored in a dedicated \texttt{RefreshToken} table.

\paragraph{Persistence and API layer.}
The complete backend was built in this phase: raw-SQL CRUD repositories for all eight entities,
a service layer enforcing business invariants (the 20-evaluation cap per chat, HMAC author token
generation, PBKDF2-SHA256 password hashing with 260\,000 iterations), and a FastAPI application
with nine route files and Pydantic schemas. A test suite of 291 tests covered all repositories
and services, including boundary cases for soft-delete cascades, composite primary keys,
password-hash opacity, JWT token lifecycle, and slug collision handling.

\paragraph{Judge architecture.}
The evaluation design required judges with different focuses. Three concrete judge classes were
implemented: \textbf{StyleJudge} (vocabulary, tone, rhetorical habits),
\textbf{IdeologyJudge} (political views, moral stances), and \textbf{GeneralJudge} (all traits
combined). Each extended an abstract \texttt{BaseJudge} with four evaluation methods ---
persona identification, individual fidelity, group fidelity, and behavioral fidelity. Prompts
were extracted from Python strings into Jinja2 \texttt{.j2} templates, making them versionable
and enforceable (every template required explicit motivation-before-rating, a 1--5 rubric, and
JSON output).

\paragraph{Persona runtime and group chat engine.}
The \texttt{PersonaAgent} class wrapped a database agent row into a live, chat-ready object.
Rather than treating all agents as identical, the class derived behavioral parameters from the
persona's own profile: \texttt{dominance\_weight} from social-positioning keywords,
\texttt{cooldown\_turns} from the rhythm field in \texttt{core\_style}, and
\texttt{burst\_size} from sentence-shape descriptors. A high-dominance agent would speak more
and recover faster; a reserved agent would yield turns naturally.

The \texttt{GroupChatSession} orchestrator connected a \texttt{TurnScheduler} (weighted-random
or round-robin) with a \texttt{ContextWindow} (rolling or selective history trimming) to run
fully autonomous multi-agent conversations. A dedicated \texttt{DMSession} handled the simpler
one-on-one path. Both modes used the same persona engine but different prompt templates.

\paragraph{First scalability wall.}
Running persona identification with three judges against a 40-message transcript and seven
personas already exceeded the local 120-second timeout. With the full design calling for twenty
judges and a database of 100+ personas, the evaluation pipeline was clearly unviable at this
scale. This problem was deferred to Phase III.

\subsection{Phase III --- Integration (May 25--27)}

Phase III was the most intensive period of the project. All major subsystems converged
simultaneously, and several assumptions from earlier phases had to be corrected under pressure.

\paragraph{The scalability problem, solved.}
The root cause of the evaluation bottleneck was that each judge had to consider every persona
in the database for every message. The fix was a Retrieval-Augmented Generation (RAG)
pre-filtering layer. Each persona's structured profile was split into typed semantic chunks
(\texttt{style}, \texttt{voice}, \texttt{worldview}, \texttt{behavior}, \texttt{quote}),
embedded with \texttt{text-embedding-3-small}, and stored in a ChromaDB index. Before scoring,
each judge queried the index to receive a shortlist of the 20 most likely candidates, ranked by
field-weighted cosine similarity and re-ranked by Maximal Marginal Relevance (to prevent a
single ``attractor'' persona from dominating the shortlist). This reduced LLM calls from
$\sim$2\,000 to $\sim$80 per run --- a 97\% reduction --- and brought latency from 33 minutes
to $\sim$30 seconds.

\paragraph{A flaw in persona identification.}
An independent issue surfaced in the evaluation logic: the greedy argmax that assigned each
persona to its highest-scoring author could assign the same author to multiple personas
simultaneously. In a chat with eight agents, a single highly distinctive author could ``win''
several persona slots, inflating accuracy artificially. The fix was to replace argmax with the
\textbf{Hungarian algorithm} (\texttt{scipy.optimize.linear\_sum\_assignment}), which
finds the assignment that maximises total score subject to the constraint that each author maps
to exactly one persona and vice versa. This change made persona identification results valid.

\paragraph{Deeper persona extraction.}
Source transcripts alone could not fully specify some persona traits --- specifically,
catchphrases and syntactic tics that are widely known but rarely appear verbatim in any
single transcript. The extraction pipeline was redesigned as a two-stage process. The first
call used \texttt{gpt-4o-mini} with the full transcript to ground all behavioral fields in real
observed speech. The second call used \texttt{gpt-4o} with \emph{no transcript} to extract
pure model-knowledge fields (\texttt{favored\_words}, \texttt{structural\_patterns},
\texttt{do\_not\_say}) from the model's parametric knowledge. Each extracted entry had to fail
a ``similar figure'' discriminability test: if the same line could plausibly come from a
confusable persona, it was discarded. The total extraction cost for 80 personas was
\textbf{\$0.57} (1.19M tokens).

\paragraph{Closing the UI gap.}
The React prototype had been running on static mock data since Phase I. In this phase, all
screens were wired to live API calls. A shared \texttt{api.js} HTTP client and an
\texttt{agents-store.jsx} React context replaced \texttt{data.js}. The admin dashboard was
connected to the evaluation output, rendering persona identification accuracy, the confusion
matrix, per-persona fidelity scores, and the turn-distribution Gini coefficient in real time.

\paragraph{MCP integration.}
To allow AI agents to interact with the platform programmatically, a Model Context Protocol
server was implemented. It exposed two tiers of tools: read-only operations requiring no
confirmation, and write operations requiring an explicit preview-then-confirm step from the
user. The LLM cannot stop a chat, launch a judging run, or post a message without the user
approving the action first.

\paragraph{Statistical evaluation engine.}
The complete \texttt{src/eval/} package was finished: four metric modules covering persona
identification (binomial exact CI, Cohen's kappa, confusion matrix), individual fidelity
(median, IQR, bootstrap 95\% CI), group fidelity (Gini coefficient, cosine distance matrix),
and deliberation convergence (variance reduction, F-test). All non-parametric estimates share
a single \texttt{bootstrap\_ci()} helper with 10\,000 resamples.

\subsection{Phase IV --- Polish and Hardening (May 28--31)}

The final phase had no single large feature. Instead, it addressed a collection of gaps and
inconsistencies that only became visible once the full system was running end-to-end.

\paragraph{Evaluation refinements.}
The admin dashboard gained Mean Absolute Deviation (MAD) between all judge-type pairs, making
systematic disagreement between style, ideology, general, and behavioral judges visible at a
glance. A batch evaluation pipeline was added to aggregate results across multiple chat
sessions: for fewer than 20 sessions it uses bootstrap resampling; for 20 or more it switches
to the Central Limit Theorem normal approximation.

\paragraph{UI and UX corrections.}
Real-world personas had been displaying their surname as the subtitle in the agent library ---
a fallback that exposed an internal implementation detail. The fix was to read the
\texttt{occupation} field from the persona's structured profile and use it as the subtitle
instead, making the library read as ``AI researcher'' rather than ``Karpathy''. Other fixes:
a pause button for group chats, filters on the chat list, responsive layout adjustments, and
a light theme.

\paragraph{MCP hardening.}
The MCP read and write tool schemas were revised to match the current API. The documentation
file was updated to reflect all available tools, their parameters, and the confirmation
protocol for write operations.

\paragraph{Knowledge graph.}
A static knowledge graph of the entire codebase was generated and committed: 6\,920 nodes and
8\,337 edges across 20 community clusters, providing a queryable map of architectural
relationships between components.

\section{System Architecture}

\subsection{Technology stack}

\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Layer} & \textbf{Technology} \\
\midrule
Backend API      & Python 3.12, FastAPI, Uvicorn \\
Database         & SQLite (raw SQL, WAL mode, FKs enforced) \\
Schema/validation & Pydantic v2 \\
Auth             & JWT (HS256), PBKDF2-SHA256, httpOnly cookies \\
LLM backend      & OpenAI (\texttt{gpt-4o-mini}) or Ollama (mistral) \\
RAG              & ChromaDB, \texttt{text-embedding-3-small} \\
Frontend         & Vanilla React/JSX, no bundler \\
Testing          & pytest, in-memory SQLite fixtures \\
MCP              & FastMCP (\texttt{src/mcp/mcp\_server.py}) \\
\bottomrule
\end{tabular}

\subsection{Layered architecture}

The backend follows a strict layered pattern:

\begin{enumerate}
  \item \textbf{Routes} (\texttt{src/API/routes/}) --- HTTP layer only. Receives requests,
        calls services, returns responses. Never touches SQL directly.
  \item \textbf{Services} (\texttt{src/db/services/}) --- Business logic. Calls repositories,
        enforces invariants (e.g.\ 20-evaluation cap, slug uniqueness).
  \item \textbf{Repositories} (\texttt{src/db/repositories/}) --- Raw SQL CRUD.
        Every entity exposes: \texttt{create}, \texttt{get}, \texttt{get\_by\_slug},
        \texttt{update}, \texttt{delete(hard=False)}, \texttt{query(filters,limit,offset)}.
  \item \textbf{Models} (\texttt{src/db/models/}) --- Python dataclasses mirroring DB tables.
\end{enumerate}

\textbf{Key invariant}: SQL lives only in \texttt{api/}. Agent and evaluation code receives
plain Python objects.

\subsection{Database schema}

The final schema (v3, implemented in \texttt{src/db/models/base.py}) comprises ten tables:

\begin{longtable}{@{}lll@{}}
\toprule
\textbf{Table} & \textbf{Purpose} & \textbf{Notable constraints} \\
\midrule
\texttt{User} & Platform users & \texttt{Role}: common|admin; slug UNIQUE \\
\texttt{Agents} & Persona profiles & \texttt{Summary}: JSON profile; \texttt{Created\_by} FK \\
\texttt{Agent\_context} & Context chunks & \texttt{Signature\_phrases}: JSON phrases \\
\texttt{Topic} & Chat themes & \texttt{Title} UNIQUE \\
\texttt{Group\_chat} & Chat sessions & \texttt{status}: pending|running|done|stopped|error \\
\texttt{Chat\_agent} & Chat$\leftrightarrow$Agent junction & Composite PK (\texttt{id\_chat}, \texttt{id\_agent}) \\
\texttt{Chat\_messages} & Messages & \texttt{author}: name+surname+DIGEST; no FK to Agents \\
\texttt{Judges} & Judge instances & \texttt{Role}: style|ideology|general|behavioral \\
\texttt{Judge\_evaluation} & Evaluation scores & Composite PK; max 20 per chat enforced in service \\
\texttt{RefreshToken} & JWT refresh tokens & Stores SHA-256 hash, never plaintext \\
\bottomrule
\end{longtable}

\paragraph{Soft-delete pattern.}
All tables have \texttt{deleted\_at}. Queries always filter \texttt{WHERE deleted\_at IS NULL}.
Hard delete is admin-only. Slug uniqueness is \texttt{UNIQUE WHERE deleted\_at IS NULL}.

\paragraph{Author anonymisation.}
\texttt{Chat\_messages.author} = \texttt{HMAC-SHA256(ANGRY\_AUTHOR\_SECRET, name:surname)}.
The hash is computed server-side by \texttt{ChatMessageService}. No foreign key from
\texttt{Chat\_messages} to \texttt{Agents} exists --- judges can distinguish different
message sources without knowing which agent sent what.

\section{Persona Extraction and Profiles}

\subsection{Source material}

\begin{itemize}
  \item \textbf{Fiction personas:} movie scripts (IMSDB HTML, PDFs), TV screenplays.
        Challenge: sparse material --- a character may have only a few dozen lines.
  \item \textbf{Real-world personas:} YouTube transcripts, podcast audio, Twitter/X threads.
        Challenge: extracting ideology and behavior from naturalistic speech rather than
        written dialogue.
\end{itemize}

Target source material: \textbf{10\,000--50\,000 tokens per persona} to capture not just
surface vocabulary but deeper patterns: argumentation style, emotional triggers, social
positioning.

\subsection{Two-phase extraction pipeline}

The extraction pipeline (\texttt{src/agents/personas/extract\_profile.py}) was redesigned
in Phase III to use two separate LLM calls:

\paragraph{Phase 1 --- Transcript-grounded fields.}
Uses \texttt{gpt-4o-mini} with the full source transcript. Extracts behavioral fields
that require grounding in real observed speech: \texttt{core\_style}, \texttt{worldview},
\texttt{self\_image\_vs\_reality}, \texttt{emotional\_tells}, \texttt{situational\_behavior},
\texttt{escalation\_pattern}, \texttt{relationship\_matrix}, \texttt{annotated\_quotes}.

\paragraph{Phase 2 --- Model-knowledge fields.}
Uses \texttt{gpt-4o} with \emph{no transcript}. Extracts fields the model knows from
parametric knowledge: \texttt{vocabulary\_fingerprint.favored\_words},
\texttt{speech\_signature.structural\_patterns}, \texttt{do\_not\_say}. Each entry must
fail a ``similar figure'' discriminability test (i.e.\ it cannot be equally attributed to
a confusable persona). Total cost for 80 personas: \$0.57 (1.19M tokens).

\subsection{Structured profile schema}

Each profile is a JSON document stored in \texttt{Agents.Summary}. Key fields:

\begin{longtable}{@{}ll@{}}
\toprule
\textbf{Field} & \textbf{Content} \\
\midrule
\texttt{core\_style} & Default register, sentence shape, rhythm, two registers \\
\texttt{humor} & Style, frequency, mechanism \\
\texttt{speech\_signature} & Naming behavior, structural patterns \\
\texttt{vocabulary\_fingerprint} & Favored words, avoided words, domain jargon, fillers \\
\texttt{worldview} & Key beliefs/values as key-value pairs \\
\texttt{self\_image\_vs\_reality} & Self-image, reality, gap behavior \\
\texttt{emotional\_tells} & When guarded, afraid, grieving, in control \\
\texttt{situational\_behavior} & When outmatched, disagreeing, protecting, proven wrong \\
\texttt{escalation\_pattern} & How the character escalates conflict \\
\texttt{conversation\_goals} & List of what the character tries to achieve \\
\texttt{relationship\_matrix} & Per-character relationship descriptions \\
\texttt{knowledge\_domains} & Expert / surface / ignorant lists \\
\texttt{social\_positioning} & Desired position, actual dynamic, contradiction \\
\texttt{annotated\_quotes} & Quote + context + what it illustrates \\
\texttt{do\_not\_say} & Lines that would break character, with reason \\
\bottomrule
\end{longtable}

\section{Context Management}

Long multi-turn conversations present three distinct problems for persona fidelity:

\begin{enumerate}
  \item \textbf{Grounding} --- the model has no inherent knowledge of the persona and must
        receive its profile on every inference call.
  \item \textbf{Character drift} --- after $\sim$30--40 turns, the conversational context
        dominates the system prompt and the agent converges toward a generic LLM voice.
  \item \textbf{Group dynamic drift} --- in group chats with 8 agents, they converge toward
        similar tone and positions (excessive agreeableness, Park et al., 2023).
\end{enumerate}

\subsection{Token budget per turn}

\begin{tabular}{@{}lr@{}}
\toprule
\textbf{Component} & \textbf{Tokens (approx.)} \\
\midrule
Structured profile (cached)   & $\sim$1\,000 \\
RAG chunks (dynamic)          & $\sim$400 \\
Compressed history (dynamic)  & $\sim$300 \\
Self-anchor / reflection      & $\sim$200 \\
Last 5 turns verbatim         & $\sim$600 \\
User message                  & $\sim$50 \\
\midrule
\textbf{Total per turn}       & \textbf{$\sim$2\,550} \\
\emph{vs.\ raw transcript}    & \emph{$\sim$30\,000} \\
\bottomrule
\end{tabular}\quad (savings $\approx$ 92\%)

\subsection{Mitigation mechanisms}

\paragraph{Sliding window + compression.}
Only the last $K = 5$ turns are passed verbatim. Every 10 turns, the older history is
compressed into $\sim$200--300 tokens via an LLM call and stored as a summary.

\paragraph{Reflection.}
Every $N = 15$--20 turns, the agent reviews its last messages against its profile and
produces a 150--200-token self-anchor injected before the next reply.

\paragraph{Perturbation (group chat only).}
Every 10--15 turns per agent, a private signal is injected: ``The conversation is moving
toward consensus. React in a way that reflects your genuine position.'' This fires on a
per-agent basis and is not visible to other agents.

\paragraph{Drift detection.}
Pairwise cosine similarity between agents' last-turn message embeddings is tracked. A
rising similarity above threshold 0.85 triggers early reflection or perturbation.

\paragraph{Prompt caching.}
The structured profile is passed with a cache breakpoint after the system prompt
(Anthropic ephemeral cache, 5-min TTL), saving 60--80\% of input token cost on the
static portion after the first turn.

\section{Chat Simulation}

\subsection{PersonaAgent}

\texttt{PersonaAgent} (\texttt{src/agents/personas/persona\_agent.py}) is the core runtime
class for a single persona in a chat:

\begin{itemize}
  \item \texttt{bind\_to\_chat(chat\_id, topic)} --- resolves profile from DB, derives
        \texttt{dominance\_weight} from \texttt{social\_positioning} keywords,
        \texttt{cooldown\_turns} from \texttt{core\_style.rhythm},
        \texttt{burst\_size} from \texttt{core\_style.sentence\_shape}.
  \item \texttt{respond(history, turn\_count)} --- renders the Jinja2 prompt template,
        calls the LLM, returns the reply string.
\end{itemize}

\subsection{TurnScheduler}

Selects the next speaking agent:
\begin{itemize}
  \item \textbf{round\_robin} --- cycles through agents in fixed order.
  \item \textbf{weighted\_random} --- samples proportional to \texttt{\_effective\_weight},
        which penalises an agent within its \texttt{cooldown\_turns} window by factor 0.1.
\end{itemize}

\subsection{GroupChatSession}

Orchestrates the full autonomous conversation loop:
\begin{enumerate}
  \item Select next agent via \texttt{TurnScheduler}.
  \item Trim history via \texttt{ContextWindow} (\texttt{rolling} or \texttt{selective}).
  \item Call \texttt{agent.respond()}.
  \item Persist message with HMAC author token via \texttt{ChatMessageService}.
  \item Repeat \texttt{burst\_size} times, reading fresh history between bursts.
  \item Check \texttt{Group\_chat.status} at each iteration --- stop if \texttt{stopped}.
\end{enumerate}

\subsection{DM chat}

\texttt{DMSession} (\texttt{src/dm\_chat/session.py}) is a simplified single-agent path with
no scheduler, no burst, no background task. Agent responds synchronously after each user
message.

\section{Evaluation Framework}

The evaluation pipeline operates in two phases and measures four fidelity dimensions.

\subsection{Four fidelity dimensions}

\begin{description}[leftmargin=3cm,labelwidth=2.8cm]
  \item[Persona ID] Can judges correctly identify which anonymous author tag corresponds to
        which persona? Baseline: 12.5\% (random over 8).
  \item[Individual] How faithfully did each agent represent its persona? Scored 1--5 per judge.
  \item[Group] Does the conversation exhibit realistic group dynamics (turn distribution,
        topic diversity)?
  \item[Behavioral] Does the conversation read as human-produced, or does it show LLM
        artifacts (excessive politeness, unnatural consensus)?
\end{description}

\subsection{Phase 1 --- Independent evaluation}

All 20 judges evaluate independently. They are divided by role:

\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Role} & \textbf{Focus} \\
\midrule
\texttt{style}       & Vocabulary, sentence structure, rhetorical habits \\
\texttt{ideology}    & Political views, values, moral stances \\
\texttt{behavioral}  & Behavioral fidelity, human-likeness \\
\texttt{general}     & All traits combined \\
\bottomrule
\end{tabular}

\paragraph{RAG pre-filtering.}
Before scoring, each judge queries ChromaDB to receive a shortlist of 20 candidate personas
(from potentially 100+). Field-weighted retrieval boosts chunks relevant to the judge's role.
MMR re-ranking ensures diversity in the shortlist.

\paragraph{Hungarian assignment.}
Author $\leftrightarrow$ persona matching uses \texttt{scipy.optimize.linear\_sum\_assignment}
to enforce a bijective assignment --- each author maps to exactly one persona.

\subsection{Statistical metrics}

\paragraph{Persona identification.}
\begin{align}
\text{accuracy} &= \frac{\text{correct guesses}}{\text{total guesses}} \\
H_0: p &= \tfrac{1}{8} = 0.125, \quad H_1: p > 0.125 \quad \text{(one-sided binomial exact test)} \\
\kappa &= \frac{p_o - p_e}{1 - p_e} \quad \text{(Cohen's Kappa, corrects for chance)}
\end{align}

\paragraph{Individual fidelity.}
Median + IQR over 20 Likert ratings per persona. Bootstrap 95\% CI on the median
(10\,000 resamples). Judge-type agreement measured by MAD between median scores per type.

\paragraph{Group fidelity.}
Gini coefficient on turn distribution:
\[
G = \frac{2 \sum_i i \cdot x_i}{n \sum_i x_i} - \frac{n+1}{n}
\]
Target range for realistic group chats: $G \in [0.28, 0.42]$ (reference mean 0.33, std 0.05).

\paragraph{Batch evaluation.}
The batch pipeline (\texttt{src/eval/batch.py}) aggregates per-chat metrics across many sessions.
CI method: bootstrap for $n < 20$ chats; CLT normal approximation
($\text{CI} = \bar{x} \pm 1.96 \cdot \sigma / \sqrt{n}$) for $n \geq 20$.

\subsection{Phase 2 --- Deliberation (design)}

Phase 2 takes high-variance cases from Phase 1 into structured deliberation:
\begin{enumerate}
  \item Identify cases where judge variance exceeds threshold.
  \item Run 3--5 deliberation rounds. Judges explain evidence, revise ratings.
  \item Track variance per round; convergence = $\text{var}_{\text{final}} < \text{var}_0$.
  \item F-test between round 0 and final round variances.
  \item Track confidence calibration: $r(\Delta\text{confidence}, \Delta\text{accuracy})$.
\end{enumerate}

\section{MCP Layer}

The Model Context Protocol server (\texttt{src/mcp/mcp\_server.py}) exposes the platform
to any MCP-compatible LLM client via structured tool calls over stdio.

\subsection{Architecture}

\begin{lstlisting}[numbers=none,frame=single]
LLM client (MCP host)
      |  tool call (JSON over stdio)
      v
mcp_server.py   [FastMCP]
      |-- tools/read.py    (Tier 1: free reads)
      \-- tools/write.py   (Tier 2: preview -> confirm)
               |
               v
         client.py  [httpx -> FastAPI :8000]
               |
               v
         SQLite DB
\end{lstlisting}

\subsection{Tool tiers}

\paragraph{Tier 1 --- Read (no confirmation required).}
\texttt{get\_agents}, \texttt{get\_agent\_by\_id}, \texttt{get\_chat\_messages},
\texttt{get\_admin\_overview}, \texttt{get\_judge\_result}, \texttt{get\_judge\_status},
and more. The \texttt{get\_agents} tool strips the \texttt{summary} field (10k--50k tokens
per agent) to prevent context overflow; full profiles retrieved by ID.

\paragraph{Tier 2 --- Write (preview $\to$ confirm).}
Every write has two tools: \texttt{preview\_*} shows the payload; \texttt{confirm\_*}
executes only after explicit user approval.

\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Preview / Confirm pair} & \textbf{Action} \\
\midrule
\texttt{create\_full\_chat} & Create DM or group chat \\
\texttt{create\_message}    & Post a message to a chat \\
\texttt{stop\_chat}         & Halt background agent loop \\
\texttt{start\_judging}     & Launch 20-judge evaluation ($\sim$\$0.40, $\sim$9 min) \\
\texttt{create\_topic}      & Create a new topic \\
\bottomrule
\end{tabular}

The LLM \textbf{never stops a chat autonomously} --- only when the user explicitly writes ``stop''.

\section{State-of-the-Art Positioning}

Five papers ground the project methodology:

\begin{description}[leftmargin=0em]
  \item[Wason et al.\ (2024)] Identifies context management and response accuracy/dialogue
        success divergence as core unsolved challenges --- directly motivating the sliding
        window, compression, and reflection mechanisms.
  \item[Salewski et al.\ (2023)] Documents demographic bias in persona prompts. Warns that
        persona prompts specifying demographic characteristics induce stereotyped behavior ---
        motivating the use of behavioral/ideological profiles rather than demographic labels.
  \item[Jiang et al.\ (2024) --- PersonaLLM] Validates that LLMs reliably encode Big Five
        trait profiles in self-reports and linguistic style. Critically: informing raters
        of AI authorship degrades personality attribution accuracy --- motivating the
        \textbf{blind evaluation protocol} (anonymised author tags).
  \item[Zhou et al.\ (2025)] Shows personal detail features are the single most critical
        driver of behavioral fidelity (removing them causes the largest accuracy drop).
        Motivates the structured profile schema.
  \item[Park et al.\ (2023) --- Generative Agents] Demonstrates memory, reflection, and
        planning for long-term coherent agents. Documents excessive agreeableness in
        group settings --- motivating the perturbation mechanism.
\end{description}

\paragraph{Novel contribution.}
No prior work integrates all four fidelity dimensions (persona identification, individual,
group, behavioral) in a unified experimental pipeline grounded in real-person text corpora.
The project's evaluation framework constitutes the novel scientific contribution.

\section{Open Questions and Future Work}

\begin{description}[leftmargin=0em]
  \item[\textbf{Deliberation (Phase 2)}]
        The phase 2 pipeline is designed (documented in \texttt{EXPERIMENTATION.MD} and
        \texttt{EVAL.md}) but not yet fully implemented. Implementing structured
        multi-round deliberation and measuring variance reduction would complete the
        evaluation pipeline.
  \item[\textbf{Behavioral fidelity}]
        Unlike persona identification (clean baseline) and individual fidelity (Likert
        scores), behavioral fidelity --- whether an agent reads as human-produced ---
        lacks an operational definition. LIWC-based psycholinguistic profiling or
        human blind raters are the most viable approaches.
  \item[\textbf{Optimal conversation length}]
        Too short ($<$20 turns) misses deep behavioral patterns; too long ($>$150 turns)
        causes drift. The empirically optimal range is not yet determined.
  \item[\textbf{Candidate set size for identification}]
        The evaluation uses a closed 8-tag set (clean baseline, 12.5\% random). An
        expanded-set design (K $>$ 8 decoy personas) would be more ecologically valid
        but reduces statistical power. Three options are analyzed in
        \texttt{evaluation\_design\_open\_questions.md}.
  \item[\textbf{RAG recall for sparse personas}]
        Retrieval recall degrades for personas with $<$5k tokens of source material.
        No mitigation is implemented for sparse profiles.
  \item[\textbf{MCP auth}]
        MCP read/write tools currently bypass FastAPI auth. The
        \texttt{Authorization} header injection needs to be added before production use.
  \item[\textbf{Prefiltering experiments}]
        Varying candidate set size for judge shortlisting and measuring the effect on
        final accuracy would quantify the RAG retrieval quality vs. judge workload
        trade-off.
\end{description}
